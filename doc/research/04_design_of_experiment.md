# Design of Experiment (DoE)

## 1. Objective

To validate the effectiveness of the multi-dimensional evaluation framework in assessing LLM-generated code quality.

## 2. Research Questions

| ID | Research Question |
|----|-------------------|
| RQ1 | How accurately does the framework detect correctness issues in generated code? |
| RQ2 | How effectively does the robustness evaluator identify consistency problems? |
| RQ3 | What types of security vulnerabilities are most commonly generated by LLMs? |
| RQ4 | How prevalent are hallucinations in LLM-generated code? |
| RQ5 | What is the correlation between different quality dimensions? |

## 3. Hypotheses

| ID | Hypothesis |
|----|------------|
| H1 | The correctness evaluator achieves >90% accuracy in detecting syntax/execution errors |
| H2 | LLM-generated code shows >80% consistency across prompt variations |
| H3 | Security issues are present in >30% of generated code samples |
| H4 | Hallucinations (fake imports/APIs) occur in >20% of generated code |
| H5 | Safety and hallucination scores are positively correlated |

## 4. Experimental Setup

### 4.1 Benchmark Dataset

**Location:** `data/evaluation/benchmark_dataset.json`

| Attribute | Value |
|-----------|-------|
| Total Tasks | 28 |
| Categories | 5 (algorithms, data_structures, string_processing, api_design, database) |
| Difficulty Levels | 3 (easy, medium, hard) |
| Language | Python |
| Test Cases per Task | 3-4 |

**Task Distribution:**

| Category | Count | Difficulty Distribution |
|----------|-------|------------------------|
| Algorithms | 6 | 2 easy, 2 medium, 2 hard |
| Data Structures | 6 | 2 easy, 2 medium, 2 hard |
| String Processing | 6 | 2 easy, 2 medium, 2 hard |
| API Design | 5 | 1 easy, 2 medium, 2 hard |
| Database | 5 | 1 easy, 2 medium, 2 hard |

### 4.2 Code Generation Configuration

| Parameter | Value |
|-----------|-------|
| Model | claude-sonnet-4-20250514 |
| Temperature | 0.7 |
| Max Tokens | 2048 |
| System Prompt | Standardized code generation prompt |

### 4.3 Evaluation Configuration

```python
EvaluationConfig:
    # Evaluators
    run_correctness: True
    run_robustness: True
    run_safety: True
    run_hallucination: True

    # Thresholds
    correctness_threshold: 0.7
    robustness_threshold: 0.6
    safety_threshold: 0.7
    hallucination_threshold: 0.7

    # Weights for overall score
    weights:
        correctness: 0.35
        robustness: 0.20
        safety: 0.25
        hallucination: 0.20
```

## 5. Metrics

### 5.1 Primary Metrics

| Metric | Description | Formula |
|--------|-------------|---------|
| **Pass Rate** | Percentage of tasks passing threshold | passed_tasks / total_tasks |
| **Average Score** | Mean score across all tasks | sum(scores) / count |
| **Issue Density** | Issues per line of code | total_issues / total_lines |

### 5.2 Per-Evaluator Metrics

| Evaluator | Specific Metrics |
|-----------|-----------------|
| Correctness | Syntax pass rate, Execution pass rate, Test pass rate |
| Robustness | Consistency score, Edge case coverage |
| Safety | Vulnerability count by severity, Top vulnerability types |
| Hallucination | Fake import count, Invalid API calls |

### 5.3 Aggregate Metrics

| Metric | Description |
|--------|-------------|
| **Overall Score** | Weighted combination of all evaluator scores |
| **Pass@k** | Probability of at least one passing in k attempts |
| **Severity Distribution** | Breakdown of issues by severity level |

## 6. Experimental Procedure

### 6.1 Execution Steps

```
1. Load benchmark dataset
2. For each task:
   a. Generate code using Claude API
   b. Run correctness evaluation
   c. Run robustness evaluation
   d. Run safety evaluation
   e. Run hallucination detection
   f. Aggregate results
   g. Save checkpoint (every 5 tasks)
3. Generate evaluation report
4. Compute summary statistics
5. Perform correlation analysis
6. Generate visualizations
```

### 6.2 Experiment Runner

**Location:** `experiments/runner.py`

```bash
# Run full experiment
python -m experiments.run_experiment

# Run with filters
python -m experiments.run_experiment \
    --categories algorithms data_structures \
    --difficulties easy medium \
    --max-tasks 20
```

### 6.3 Output Structure

```
experiments/results/exp_YYYYMMDD_HHMMSS/
├── config.json              # Experiment configuration
├── raw_results.json         # Complete task results
├── evaluation_report.json   # Evaluation details
├── summary.json             # Summary statistics
├── checkpoints/             # Periodic checkpoints
└── plots/                   # Generated visualizations
```

## 7. Analysis Plan

### 7.1 Descriptive Statistics

For each evaluator:
- Mean, median, std deviation of scores
- Pass rate
- Issue count and severity distribution

### 7.2 Comparative Analysis

- Performance by category
- Performance by difficulty level
- Evaluator score distributions

### 7.3 Correlation Analysis

- Pearson correlation between evaluator scores
- Identify relationships between quality dimensions

### 7.4 Failure Pattern Analysis

- Most common issue types
- Category-specific failure patterns
- Difficulty-related trends

## 8. Visualization Plan

| Visualization | Purpose |
|---------------|---------|
| Box plots | Score distributions per evaluator |
| Bar charts | Pass rates by category/difficulty |
| Heatmap | Evaluator correlation matrix |
| Stacked bars | Issue severity breakdown |
| Line plots | Score trends across difficulty |

## 9. Reproducibility

### 9.1 Environment Capture

Each experiment records:
- Git commit hash
- Python version
- Platform information
- Package versions (anthropic, chromadb, etc.)
- Dataset SHA-256 hash

### 9.2 Checkpointing

- Checkpoints saved every 5 tasks
- Enables experiment resumption
- Full state preservation

### 9.3 Seed Control

- Random seeds fixed where applicable
- Temperature set consistently
- Deterministic evaluation logic

## 10. Expected Results

### 10.1 Anticipated Findings

| Dimension | Expected Range | Rationale |
|-----------|---------------|-----------|
| Correctness | 0.6 - 0.8 | LLMs generally produce working code |
| Robustness | 0.5 - 0.7 | Some inconsistency expected |
| Safety | 0.7 - 0.9 | Most code avoids obvious vulnerabilities |
| Hallucination | 0.7 - 0.9 | Occasional fake imports expected |

### 10.2 Success Criteria

The experiment is successful if:
1. All evaluators produce meaningful, discriminative scores
2. Correlation analysis reveals expected relationships
3. Results are reproducible across multiple runs
4. Identified issues are actionable and correct
